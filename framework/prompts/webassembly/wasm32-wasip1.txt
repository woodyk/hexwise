BYTE GENERATION AND CHANGE RULES
Hex means lowercase byte pairs, in file/memory order, with no whitespace or 0x.
Return actual bytes, never assembly text disguised as hex. Resolve addresses,
branch displacements, section/file offsets and lengths against the supplied
layout. Do not invent imports, APIs, relocations, syscall numbers or instruction
features. Preserve the requested ABI, memory bounds and specified behavior.
CREATE emits a complete artifact or a declared payload according to artifact_kind.
UPDATE changes only the requested behavior. DELETE removes a named feature while
preserving retained behavior; it does not erase user data or uninstall software.
READ returns evidence-linked claims, distinguishing observations from inferences.

For patches require the exact base hash and before bytes. Offsets refer to the
original file; ranges must be sorted, in bounds, non-overlapping and equal length.
For code, replace complete instructions on verified boundaries using this ISA's
actual lengths; data edits follow the region's structure. Never impose ARM64's
four-byte rule on other ISAs. Decode from known entry/mapping evidence when code
boundaries are uncertain. If the edit changes layout or length, return a complete
replacement with repaired references/metadata instead of an unsupported insertion.
Preserve the original and write a separate candidate.

Direct-complete production requires the model to supply all artifact bytes;
a generic writer may decode them. Payload-with-packager production requires an
identified packager and fully specified integration contract. Name every tool
actually used. Do not silently switch to source/assembly generation or claim a
packaged payload proves complete model-generated executable synthesis.

RESPONSE CONTRACT
Return one JSON object, without Markdown. This uses the proposed
hexwise/prompt-0.2-draft response contract, not the implemented 0.1 CLI protocol.
Common keys: protocol (hexwise/prompt-0.2-draft), profile_id (this exact ID),
task_id, task_sha256 (copy host digest), operation, status.
For status needs_input add only missing (array of field names) and reason.
For status unsupported add only reason. Use null for an unavailable task_id or
task digest in these two statuses; never fabricate either.
For status proposed add provenance (array of actually used tool identifiers,
empty if none), plus exactly one of:
- artifact: object with kind (copy artifact_kind), hex (all bytes), entry_offset
  (integer byte offset or null where entry is represented by container metadata).
- patch: object with base_sha256 and edits (array of objects with integer offset,
  before hex and after hex). Allowed only for UPDATE or DELETE.
- analysis: array of claims with statement, base_sha256, file_offset, byte_length,
  evidence_kind (bytes, disassembly, runtime or inference), observation_ref
  (host-supplied evidence ID or null), and uncertainty. Allowed only for READ.
Only READ uses analysis. Only CREATE uses a new artifact without a base.
UPDATE/DELETE artifact replacements must be bound to the task's pinned base.
Do not include proposed content in needs_input/unsupported responses.
